# Бенчмарк подбора номенклатуры

Подбор изделий под требования закупки — отдельная задача от извлечения PDF.
Бенчмарк не использует прежние знаменатели 500/520 инженерных фактов.

## Что оцениваем

Для каждой строки требования независимый инженер назначает один эталонный статус:

- `exact` — конкретный SKU точно удовлетворяет требованиям;
- `expert_review` — возможен эквивалент, но требуется инженерное решение;
- `no_candidate` — подтверждённого подходящего SKU в доступном срезе нет;
- `insufficient_data` — исходных требований или характеристик недостаточно.

Эталонный выбор `exact` должен содержать product ID и ссылки на источник требования,
подтверждение инженера или реальный результат закрытой закупки. Кандидат системы,
выбранный только по сходству названия, не создаёт эталон. Ложный выбор считается
ложноположительным даже тогда, когда его название похоже на закупочную позицию.
Для потенциальных аналогов безопасное решение — `review`, а не автоматический выбор.

Grader хранится в `src/catalog_bench/forenergo_selection.py`. Он читает CSV-free JSONL
или одну книгу `.xlsx`: в листе `Позиции` эталонные поля инженера и поля выхода
системы разделены. Время, токены, модель и версию программы он сохраняет отдельно.
Пример JSONL-формата:

```json
{"request_id":"17","gold_status":"exact","product_ids":["sku-17","sku-17b"],"evidence_refs":["tender.xlsx#sheet=Items&row=17","engineer-review#row=17"]}
{"request_id":"17","decision":"select","product_id":"sku-17","system_id":"forenergo-selector","system_version":"1.2.3","evidence_refs":["catalogue.xlsx#sheet=Товары&row=42"]}
```

Для каждой строки вывода требуются `system_id` и `system_version`; у выбора дополнительно обязателен
`product_id` и источник доказательства. Эталон может перечислять несколько точно допустимых SKU. В Excel-шаблоне эти поля доступны рядом с каждым запросом, а экспертная разметка хранится отдельно. В отчёте отдельно показаны точность среди
выбранного, recall точных SKU, покрытие, безопасные отказы, необходимость эксперта,
ложные рекомендации и строки с ещё не установленным эталоном. Пустой или неполный
эталон нельзя превратить в нулевую ошибку или в accuracy.

## Первый сбор исходных данных

`forenergo-selection-bench prepare` создаёт приватную книгу для
построчного экспертного и системного результата. Выход намеренно разрешён только в
игнорируемом `.tmp/`; рабочие документы не попадают в пакет или Git.

```bash
uv run forenergo-selection-bench prepare \
  --requests requests.xlsx \
  --appendix appendix.xlsx \
  --catalogue catalogue.xlsx \
  --output .tmp/selection/intake.xlsx
```

Точное сопоставление имён нормализует Unicode, регистр и пробелы, сохраняя знаки и
цифры. Оно проверяет лишь связь между двумя источниками; это не матчинг изделий.

Для готовой заявки с отдельным листом позиций и сохранённой книгой подбора
используется `prepare-case`. Команда связывает позиции по явному номеру и точному
нормализованному имени, сохраняет исходные строки поставки и записывает candidate
как неатрибутированный артефакт. Книги без сведений о генераторе не получают
выдуманную версию; эталоны остаются `pending`.

```bash
uv run forenergo-selection-bench prepare-case \
  --technical-workbook tender.xlsx \
  --candidate-workbook selection.xlsx \
  --catalogue catalogue.xlsx \
  --output .tmp/selection/case-intake.xlsx
```

Reader сбрасывает только некорректный XLSX used-range перед чтением фактических
строк, поэтому книги с `dimension=A1` не превращаются в фиктивный одноячеечный
каталог. Сопоставления по сходству названий не создаются автоматически.

Затем, после заполнения раздельных полей эксперта и системы, книга оценивается
без повторного вызова модели. Эталон и результат могут быть в одной книге или
в разных книгах; JSONL также поддерживается:

```bash
uv run forenergo-selection-bench score \
  --gold .tmp/selection/intake.xlsx \
  --candidate .tmp/selection/intake.xlsx \
  --output .tmp/selection/score.json
```

## Ограничения текущего цикла

Точность по реальному сохранённому результату остаётся `null`, пока не получены
подтверждённые метки инженера или факт выбранных/принятых товаров и версия системы.
Неполный источник или несогласованность имени документа с внутренним титулом
остаётся отдельной пометкой и не переносится в эталон автоматически.

Будущий этап генерации документов вносится как отдельная фаза roadmap. Он будет
принимать только утверждённую таблицу выбора и проверять поля форм/источники отдельно
от точности подбора.
